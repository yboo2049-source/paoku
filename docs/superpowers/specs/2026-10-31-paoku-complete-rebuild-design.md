# paoku 整体重构设计稿 v0.1

日期：2026-10-31。状态：待用户评审，尚未批准实施。

## 1. 目标与决策边界

将现有 Web 3D 跑酷游戏重构为视觉统一、动作可信、路线有趣、交互完整的作品。范围包括场景、人物、动画、镜头、材质灯光、火车与斜坡、道具、关卡编排、音效、全部 UI、状态管理、存档和验证体系。

核心体验假设：玩家提前读懂路线，连续完成换道、跳跃、滑铲、上坡与车顶穿行，从准确操作中获得节奏感和奖励。失败应能看懂原因，重开应足够直接。

已确认：用户要求全面重构，当前阶段先做规划。已有平台为 Vite + TypeScript + Babylon.js，桌面键盘与移动触摸均纳入设计。暂按休闲玩家、短局反复挑战设计，目标用户与单局时长仍待确认。

本稿提出设计方向和阶段验收，不是已获批准的实现任务单。采用 brainstorming Architectural 路径；评审通过后再编写 writing-plans 任务级计划。沿用项目 docs 目录作为交付位置。

## 3. 整体路线选择

| 路线 | 优点 | 代价 |
|---|---|---|
| A：整体设计、逐段替换（建议） | 每阶段都有可玩结果；旧版可作行为对照；统一最终品质 | 需要适配边界与迁移期管理 |
| B：独立新版本重建 | 新架构自由度高 | 现有能力须重新迁移，较晚才能完整对比 |
| C：各模块独立翻新 | 任务易拆分 | 风格与跨模块行为容易不一致，整体验收较晚 |

建议采用 A，先实现完整可玩样板再扩大内容。全面覆盖不意味着同一批次改完所有模块。

## 4. 美术方向候选

以下均为提案，尚未冻结风格、色号或人物比例。首轮概念小样需同时展示人物、火车、坡道、环境与 HUD，避免各自好看但同屏失衡。

| 方向 | 具体表现 | 取舍 |
|---|---|---|
| A：明亮的风格化城市轨道（建议） | 清晰轮廓、柔和阴影、克制金属反光；暖色人物与冷色环境分离；站台、轨道街区、检修区形成变化 | 易建立路线可读性；需要替换现有霓虹主视觉 |
| B：黄昏工业都市 | 暖光与冷阴影，厚重列车、机械结构、工业建筑 | 氛围与空间较强；暗部与危险物分离要求更高 |
| C：克制的夜间赛博都市 | 深色环境、局部灯光、有限霓虹强调；明确压低非交互物体亮度 | 接近现有主题；更需限制发光与信息噪音 |

共同规范：原创角色与资产；统一比例、材质家族、色彩语义、光照方向及 UI 语言。危险、奖励、可通行表面除颜色外也有形状区分。高亮效果不得盖住障碍轮廓。最终色板以同屏小样评审后写入规范。

## 5. 人物、动作与镜头

人物交付应包含一致的骨架、朝向、比例、脚底基准和动作命名。正式动作覆盖待机、奔跑、起跳、滞空、落地、滑铲进入/维持/退出、左右换道、受击与失败；滑板等特殊状态另设明确姿态。

动作由模拟状态与事件驱动：落地以接触支撑面为依据，包含地面、坡道和车顶；动画完成不决定物理是否落地。默认采用原地动作，由模拟控制位移，防止 root motion 重复位移。脚底漂移、循环接缝、动作打断、暂停恢复均需录屏验收。整模缩放只能作为有幅度限制的附加反馈，不能替代骨骼动作。

镜头设置独立的目标高度、跟随缓冲、前视距离和视野安全区；坡道与车顶高度变化不得直接造成剧烈跳镜。换道倾斜、落地震动、速度 FOV 变化应可调并支持低动态反馈设置。世界弯曲属于可选表现实验，需证明不损害路线判断再采用。

## 6. 场景、火车、斜坡与道具

场景按近、中、远景分层，并拆为可循环拼接的主题段落。近景服务通行判断，中景提供站台与街区特色，远景建立方向与空间。先完成一个主题，再扩展其他主题；接缝与重复节奏必须在长距离运行中检查。

火车包含统一尺度的车头、车厢、车窗、底盘和车顶。可站立车顶需要清晰视觉语义；车顶装饰不能产生视觉障碍与实际碰撞不一致。静态与迎面行驶列车共享资产族，通过运动、灯光及提示共同区别。

斜坡使用真实斜面；坡脚、坡顶与相邻车顶共享连接数据。接缝不能只靠额外免死阈值掩盖。金币沿有效路线布置；磁铁、双倍积分、跑鞋、滑板各自具备可辨识外形、拾取反馈、持续状态和结束提示。

资产流程：统一规格 → 小样 → 引擎内验证 → 批量制作 → 导入检查。几何占位用于验证尺度，正式品质验收必须使用目标资产。模型来源、许可证、动画可用性和制作方式逐项登记；AI 概念图不作为已完成 3D 资产。

## 7. 模拟与关卡契约草案

统一坐标：X 横向，Y 高度，Z 前进。单位和速度显示须明确换算；实体尺寸、视觉尺度与碰撞代理使用同一配置来源。

建议数据模型（语义草案，非当前代码接口）：

| 数据 | 必要信息 | 责任 |
|---|---|---|
| PlayerMotion | 位置、速度、动作阶段、支撑面 ID、接触状态 | 唯一角色运动事实 |
| Surface | ID、所属实体、横纵范围、起止高度、表面运动 | 求接触点高度与支撑速度 |
| ObstacleDefinition | 视觉资产 ID、尺度、碰撞代理、支撑面、交互类型 | 对齐可见物与规则 |
| TrackSegment | 入口/出口车道与高度、长度、速度范围、实体布局、合法路线 | 描述可拼接关卡单元 |
| RunState | 局 ID、种子、输入序列、成绩、金币、结束原因 | 重现一局及单次结算 |
| PresentationEvent | 事件 ID、模拟时刻、动作/接触/拾取信息 | 驱动动画、音频、特效和 UI |

模拟顺序建议：消费输入 → 更新移动障碍 → 运动积分 → 扫掠接触与支撑解析 → 拾取/伤害/道具结算 → 发出事件 → 输出只读表现快照。固定模拟步长与渲染插值分离；步长、最大补步量和超时策略经压力测试确定。超时不能通过无限补步冻结页面；暂停恢复须清空不合适的累计时间。

支撑面需要同时检查横向范围、纵向范围、接近方向及角色脚底高度。坡面高度按起止高度插值，加入实体基准高度；车顶跳离后不能被提前吸回。高速运动评估相对位移的扫掠碰撞，测试覆盖薄障碍与迎面列车。

关卡编排采用可复现种子及节奏阶段：教学/进入节奏 → 连续操作 → 风险奖励分支 → 缓和。拼接检验入口出口与速度条件；抽样模拟验证至少一条可达路线。有限抽样不宣称证明所有随机组合安全，失败种子应保存为回归用例。金币与道具需验证可达且不嵌入障碍。

## 8. UI、音频与数据流程

完整设计加载、主菜单、局内 HUD、暂停、结算、商店与设置；覆盖正常、加载、失败、空内容及禁用状态。菜单突出角色与开始操作，HUD 保留前方路线和人物视野，结算清楚解释成绩、收益和失败原因。

统一字体、数字宽度、间距、图标、按钮四态和弹窗层级。桌面横屏与手机竖屏分别布局；触摸目标、安全区与文本换行按 CSS 实际尺寸验证，不机械照搬美术稿像素。道具展示名称、图标与剩余时间，Toast 使用有上限的队列。

输入命令 → 状态/交易服务 → 数据快照 → UI 展示。UI 不反读文本做结算，不直接写模拟状态。结算以局 ID 保证幂等；存档有版本号、旧数据迁移与损坏回退规则。商店交易必须同时验证余额和所有权。

音频响应同一套动作与接触事件，形成脚步、起跳、落地、滑铲、金币、道具、迎面列车和失败反馈。暂停、返回菜单、重开、音量设置均有生命周期规则；不能出现音效残留或重复播放。

## 9. 目标架构与迁移

保留 Babylon.js 作为当前建议基线，换引擎只有在明确证据说明必要时另立决策。

模拟层：输入命令、角色运动、接触碰撞、道具效果、关卡编排、局内状态。表现层：资产注册、场景段落、角色动画、镜头、实体表现、特效和音频。应用层：页面状态、结算、存档和商店交易。UI 仅展示和发命令。下层禁止依赖 DOM 或 Babylon Scene。

迁移按同一模块逐步替换，旧行为保留测试作对照；旧缺陷不能因对照测试而被固化。接口更新由 Dispatcher 统一写入文档，再分派单一职责任务。每批改动可独立回退；存档迁移须有兼容测试。

## 10. 阶段路线图与交付门槛

| 阶段 | 交付 | 完成门槛 |
|---|---|---|
| M0 现状基线与定调 | 实际试玩问题清单、固定场景截图/录屏、三方向对比、资产盘点、设备基线 | 风格及完整样板范围获得评审；文档坐标与事件冲突有明确解决方案 |
| M1 契约与模拟基础 | 新数据契约、先行测试、支撑面、接触、可复现关卡、状态结算边界 | 地面→坡道→车顶→跳离→落地路径及异常输入验证通过 |
| M2 完整可玩样板 | 一个原创角色、一种完整场景、火车/坡道/障碍/金币/代表道具、正式动作、镜头灯光音效、HUD 和开始/结算流程 | 可以真实输入完成整条路线，并从录像验证目标品质；占位资产不得冒充最终样板 |
| M3 全内容扩展 | 全道具、更多段落、商店设置、完整页面和存档迁移 | 旧功能迁移清单逐项验收；跨段连接及多分辨率正常 |
| M4 性能与交付收口 | 画质档位、加载优化、长跑测试、错误恢复、回归报告 | 所有门禁通过，真实截图人工检查，目标设备性能达到约定预算 |

样板建议为 60–90 秒固定路线（提案值，验证路线覆盖而非最终单局时长）：启动与简单换道 → 跳低障碍/滑铲 → 上坡接车顶 → 车顶跨越 → 落回轨道 → 躲避迎面列车 → 道具拾取及结束 → 失败、结算、重开。

工作可在契约冻结后并行：核心 Agent 负责模拟调度；物理 Agent 负责接触和生成；渲染 Agent 负责资产、场景、角色与镜头；UI Agent 负责页面和反馈；QA Agent 先提供回归传感器并独立复核。共用文件与接口变更由 Dispatcher 串行协调。

## 11. 验收矩阵

| 编号 | 验收对象 | 方法与通过条件 |
|---|---|---|
| R-01 | 模型与支撑面 | 显示调试碰撞代理，坡脚/坡顶/车顶接缝逐一验证，无可见穿入或悬空 |
| R-02 | 接触与高速 | 不同帧时间、速度、跳跃方向、移动列车和薄障碍回归，无漏判/重复伤害 |
| R-03 | 动作 | 固定机位录制所有阶段与打断，检查脚底、循环接缝、暂停恢复和车顶落地 |
| R-04 | 路线 | 固定种子测试入口出口、可达路线、金币与道具位置，保存失败种子 |
| R-05 | 视觉 | 同屏检查风格、明暗层次、障碍可读性；人物、HUD、特效不遮挡关键路线 |
| R-06 | UI 全流程 | 真实输入走通开始、暂停、继续、结束、重开、商店、返回；无点击穿透与裁切 |
| R-07 | 结算存档 | 重复结束/返回不重复记账；旧版本数据和损坏数据可处理 |
| R-08 | 音频生命周期 | 暂停、结束、菜单切换及重开无残留与重复实例 |
| R-09 | 性能 | 记录设备、浏览器、分辨率、画质及测量区间，报告帧时间分位数、加载和内存趋势 |
| R-10 | 工程交付 | npm run build、npm run test、npm run test:e2e 全部通过，并查看真实截图 |

性能候选目标为主目标设备稳定 60 fps、较弱设备降档 30 fps；这些是待测目标，不能当成实测成绩。M0 冻结具体设备、分辨率、加载预算、资产与 draw call 预算后，才能据此验收。先测首屏、样板最密集段、反复重开及长跑内存趋势。

当前 Playwright 配置含 Metal 后端参数，Windows 基线执行时须核实实际 WebGL 可用性。测试通过与截图不空白都不能单独证明视觉品质达标。

## 12. 待评审决策与下一步

建议批准的组合：整体设计逐段替换 + 明亮风格化城市轨道 + 完整可玩样板先行。美术方向也可选择黄昏工业或夜间赛博，后续资产与灯光方案据此统一。

设计评审还需明确主要目标设备、用户群与期望单局节奏；没有实测依据前不承诺具体工期。资产制作是独立工作量，不以生成代码替代建模与动画验收。

本稿批准后：同步核心文档为执行基线，编写任务级实现计划与文件白名单，先建立现状截图和回归测试，再开展实现。每个代码任务通过项目规定的编译、单测、E2E 和视觉验收后自动提交推送。
